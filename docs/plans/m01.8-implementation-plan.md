# M01.8 — Live analytics, quality and launch (implementation plan)

## Context

M01.8 is the final epic of **M01 – Product Analytics**. Everything upstream is built and verified
(M01.1 definitions → M01.7 dashboard, commit `70eb79f`). This epic closes the module with three
capabilities the pipeline still lacks and one real-world milestone:

1. **Live/realtime visibility** — a "visitors right now + current pages" panel. Nothing realtime exists;
   there is no SignalR anywhere in the repo, and `Redis` is wired into `services/analytics` but used
   only by `QueryCache`. Plan §9 explicitly reserves Redis for "short-lived live visitor projections".
2. **Data-quality visibility** — accepted / rejected / duplicate / bot / delayed / failed event counts.
   Today there are **no counters of any kind**; only `events.is_bot` (ClickHouse) and the on-demand
   `tools/reconciliation-report` expose anything. M01's acceptance criteria include "raw and processed
   event counts can be reconciled".
3. **Real geography** — `IGeoLookup` is still `NoOpGeoLookup`; `events.country` /
   `daily_geography_rollup.country` are 100% empty. `GeographyTable.vue` already renders a "not
   available yet — M01.8" empty state. `definitions-and-privacy-model.md` §7 flags a final Dutch/EU
   guidance check "before the anthony-air.nl launch (M01.8)".
4. **The launch** — the user is acquiring **`telumera.nl`** and will host Telumera on their NAS the same
   way `anthony-air.nl` runs (Docker on the NAS → Cloudflare Tunnel → Nginx Proxy Manager). `anthony-air.nl`
   becomes the first *tracked site* (the customer), not the host. No `docker-compose.nas.yml` /
   reverse-proxy / tunnel config exists yet — `nas-deployment-profile.md` is the plan to build against.

The prior session's plan for this epic was lost before it was written to disk (nothing in the repo,
memory, scratchpads, or git). This document reconstructs it from `planning/Telumera_Asana_Import.csv`
rows 124–134 plus the architecture docs.

## Workstream A — Live visitor projection + SignalR

**A1. Redis projection (`services/analytics`).**
- New `LiveVisitorProjection.cs` — wraps `StackExchange.Redis` `IDatabase` (add explicit
  `StackExchange.Redis` package + `AddSingleton<IConnectionMultiplexer>(ConnectionMultiplexer.Connect(...))`
  in `Program.cs`; `AddStackExchangeRedisCache` registers only the cache, not the multiplexer).
- Per site: a Redis **sorted set** `live:{siteId}` scored by `receivedAt` epoch, member = `visitorId`,
  plus a companion hash `live:{siteId}:paths` (`visitorId` → last `path`). Rolling window
  `Live:WindowSeconds` (default **300** — "last 5 minutes", matching Plausible-style "current visitors").
- Written from `EventProcessor.ProcessAsync` **after** the successful ClickHouse insert (it already has
  `siteId`, `visitorId`, `path`, `receivedAt`, `isBot`). **Bots excluded** (`isBot == 0` only).
- Read: `GetSnapshotAsync(siteId)` → `ZREMRANGEBYSCORE` to trim expired, then `ZCARD` +
  top-N paths grouped → `LiveSnapshot(int ActiveVisitors, IReadOnlyList<LivePage> Pages)`.
- No persistence, no authority — a lost Redis is a cosmetic outage, not data loss.

**A2. SignalR hub (`services/analytics`).**
- `LiveHub.cs : Hub` — `MapHub<LiveHub>("/hubs/live")` in `Program.cs`, `.RequireAuthorization("ApiScope")`.
- Client calls `Subscribe(siteId)` → hub runs the **same** `QueryAuthorization.AuthorizeSiteReadAsync`
  check the REST endpoints use (needs `SiteLookupClient` + `MembershipClient`, already DI-registered),
  then `Groups.AddToGroupAsync(ctx.ConnectionId, $"site:{siteId}")`.
- A `LiveBroadcastService : BackgroundService` (`PeriodicTimer`, `Live:BroadcastIntervalSeconds`
  default 5 — copy the `SiteProjectionSyncService` shape) pushes `LiveSnapshot` to each active
  `site:{siteId}` group via `IHubContext<LiveHub>`.
- Auth over WebSocket: SignalR reads the bearer from the `access_token` query-string param for WS
  transports — standard `JwtBearerEvents.OnMessageReceived` wire-up in `Program.cs`, scoped to paths
  starting `/hubs`.
- **CORS**: add an `AddCors` policy on `analytics` (`Cors:AllowedOrigins`) with `.AllowCredentials()`
  — required for the SignalR handshake. Dev: `http://localhost:5173`. Prod: `https://telumera.nl`
  (cross-origin — dashboard at the apex, hub at `hubs.telumera.nl`).

**A3. Dashboard client (`apps/dashboard-web`).**
- Add `@microsoft/signalr` to `package.json` (first realtime dep; traffic chart stays hand-rolled).
- `src/lib/live-connection.ts` — builds a `HubConnection` to `VITE_HUBS_ORIGIN` + `/hubs/live`
  (dev `http://localhost:5104`, prod `https://hubs.telumera.nl`),
  `accessTokenFactory: () => auth.getAccessToken()`, automatic reconnect.
- `src/components/analytics/LiveVisitorsPanel.vue` — a pulsing dot + big active count + a short
  current-pages list. Mounted at the top of `SiteAnalyticsView.vue`, above the metric cards. Reuses
  the housestyle card string + `StateMessage` for the disconnected state.
- `src/lib/analytics-types.ts` — add `LiveSnapshot` / `LivePage` mirroring the C# records.
- i18n: `analytics.live.*` keys in `en.json`.

**A4. Definitions doc.** New `definitions-and-privacy-model.md` **§9 "Live visitor projection"**: 5-minute
rolling window; Redis-only, never persisted, explicitly non-authoritative; bot traffic excluded;
never feeds any historical metric; no cross-day linkage (uses the same daily visitor hash as everything
else). This is the "without treating it as durable truth" the CSV task calls for.

**Acceptance:** post events through the collector for a site, open its analytics screen in a real
browser, watch the live count rise and the current-page list update within ~5s without a page reload;
stop posting, watch it decay to 0 after the window; a non-member connection is rejected by the hub.

## Workstream B — Data-quality pipeline + dashboard

**B1. Quality dimensions & where they're known.**

| Dimension | Owned by | Signal |
|---|---|---|
| `accepted` | collector | event enqueued to the publish channel |
| `rejected_validation` / `rejected_unknown_token` / `rejected_origin` / `rejected_module_disabled` | collector | the existing branch points in `Program.cs` (`EventValidation` fail, 404, 403, `!EnabledModules.Contains("Analytics")`) |
| `duplicate` | collector **and** analytics | `DuplicateEventCache.TryClaim` false (collector, in-window) + `TryBeginProcessingEventAsync` false (analytics, cross-restart) |
| `dropped_overload` | collector | `channel.TryEnqueue` false |
| `bot` | analytics | `BotDetector.IsBot` → `events.is_bot` |
| `delayed` | analytics | event whose `receivedAt` is older than the current aggregation watermark when processed (add the check in `EventProcessor`) |
| `failed` | analytics | depth of `dlq-analytics-collector-events` (RabbitMQ management API, like `tools/dead-letter-recovery`) |

**B2. Capture (both services).**
- Add an `OpenTelemetry` `Meter` per service (`Telumera.EventCollector` / `Telumera.Analytics`) with a
  `Counter<long>` per dimension, tagged `site_id`. Register in each `Program.cs`; the OTel wiring in
  `packages/dotnet-service-defaults` already exports meters when `OTEL_EXPORTER_OTLP_ENDPOINT` is set.
  This gives live operability for free.
- **Persisted rollup**: `event-collector` gains a `QualityRollupPublisher : BackgroundService`
  (`PeriodicTimer`, `Quality:PublishIntervalSeconds` default 60) that drains its in-memory
  per-`(siteId, dimension)` counters and publishes a **`collector.quality.v1`** CloudEvent to a new
  `quality-events` pub/sub topic. Additive event contract in `packages/event-contracts`
  (`EventTypes.CollectorQualityV1`, `dataVersion: 1`).
- `services/analytics` subscribes to `quality-events` (`POST /subscriptions/quality-events`,
  `.WithTopic("pubsub", "quality-events")`, unauthenticated like the collector-events handler) and
  UPSERTs into a new ClickHouse table.

**B3. Storage (`services/analytics` / `ClickHouseWriter.EnsureSchemaAsync`).**
- `event_quality_daily` — `ReplacingMergeTree(updated_at)`, `ORDER BY (site_id, date, dimension)`,
  columns `site_id UUID, date Date, dimension LowCardinality(String), count UInt64, updated_at DateTime64(3)`.
  Collector-owned dimensions come from the subscription; analytics-owned dimensions (`bot`, `delayed`)
  are recomputed by a new step in `AnalyticsAggregationService.RunOnceAsync` scoped to the same dirty
  `(site, date)` buckets it already computes; `failed` is written by a small periodic DLQ-depth poll.

**B4. Query endpoint (`AnalyticsQueryEndpoints.cs`).**
- `GET /sites/{siteId:guid}/analytics/quality?from&to` — copy an existing handler verbatim:
  `AuthorizeSiteReadAsync` → `DateRangeParsing.Parse` → `QueryCache.GetOrSetAsync` →
  `ClickHouseQueryClient.QueryAsync` against `event_quality_daily FINAL`. Returns
  `QualityResponse(IReadOnlyList<QualityDayPoint> Series, QualityTotals Totals)` where each point is a
  date + a `Dictionary<string,long>` of dimension→count. Rides the **existing**
  `/sites/{id}/analytics/**` gateway carve-out — no gateway change.
- DTO in `AnalyticsQueryDtos.cs`, mirrored into `analytics-types.ts`.

**B5. Dashboard screen (`apps/dashboard-web`).**
- New route `/sites/:id/analytics/quality`, name `site-analytics-quality`, lazy component
  `views/SiteQualityView.vue`. Reachable from a tab/link on `SiteAnalyticsView.vue` (not a top-level
  sidebar item — it's per-site).
- `components/analytics/QualityChart.vue` — stacked bars per day (accepted vs. each reject reason vs.
  bot/delayed/failed), hand-rolled SVG in the `TrafficChart.vue` style. Run the **`dataviz` skill**
  palette validator before choosing the stack colors (green for accepted, the categorical set for the
  problem dimensions — never red-only).
- `components/analytics/QualitySummaryCards.vue` — `MetricCard` reuse: acceptance rate, duplicate rate,
  bot share, failed count, each with the glossary hook.
- i18n `analytics.quality.*`; `AnalyticsDateRangeControl.vue` reused as-is.

**B6. `tools/reconciliation-report`.** Extend its output to also read `event_quality_daily` for the day
and show accepted(collector) vs. stored(ClickHouse) vs. processed(Postgres) side by side — turning the
existing three-number report into the authoritative "reconcile raw vs processed" check M01's
acceptance criteria name.

**Acceptance:** drive a mix of good, malformed, duplicate, bot-UA, and unknown-token events through
the collector; `GET .../analytics/quality` returns each dimension with the right counts for today; the
quality screen renders the stacked history; `reconciliation-report` shows the three counts reconciling
(equal, or a documented crash-window delta).

## Workstream F — Synthetic acceptance traffic + reconciliation

**F1. `tools/synthetic-traffic`** (new, `tools/*` bare-console pattern). Drives the **real**
SDK→collector path (not `seed-demo-data.sh`, which writes fake `bootstrap_*` rows directly). Given a
site token + collector URL + a small set of scripted "journeys" (landing → 2–3 pages → a custom event;
a bounce; a bot UA; a duplicate id; a malformed event; an unknown token), it POSTs batches to
`/v1/events` and prints the **expected** metric deltas (sessions, engaged sessions, page views per
path, rejected count, bot count).

**F2. Reconcile.** After a run, `tools/reconciliation-report --date today` on the same environment must
show accepted == stored == processed (± the documented marker-before-write crash window, which a clean
run won't hit), and the quality endpoint's dimensions must match F1's printed expectations. This is the
"run synthetic acceptance traffic and reconcile expected metrics" CSV task, executed against both local
and the NAS.

**F3. Install on portfolio staging.** Add the generated snippet to the `anthony-air.nl` Vue portfolio
(`projects/Portfolio/Vue-portfolio/`, `environment: 'staging'` first), deploy via its existing
pipeline, click through real routes, and confirm in the Telumera dashboard: routes tracked, referrers
normalized, UTM captured, `excludeRoutes` honored, nothing sent before consent if `consent: 'required'`.
Then promote to `environment: 'production'`.
